# Future Pantheon migration

This is a handoff for an authorized UC Berkeley site owner and technical steward. The local prototype is the review deliverable. Hosting selection, domain changes and production migration require separate institutional approval. January 2027 is a tentative transition window.

Pantheon's published GitHub documentation was checked on November 19, 2026. The project environment could access that documentation source and the official WordPress upstream, while the hosted documentation and Berkeley hosting pages returned a proxy denial. Berkeley eligibility, pricing, account permissions and domain approval remain to be confirmed with campus staff. [Pantheon documentation source](https://github.com/pantheon-systems/documentation/tree/main/src/source/content)

## Account, sandbox and production

- Julie or designated Berkeley staff own or request access to the institutional workspace and designate a technical steward and backup. Confirm sponsorship, billing, support, hosting terms and domain eligibility with campus staff. Grant named users the minimum access needed.
- Pantheon's standard free account permits sandbox sites for non-production work. Dev is for integration and Test is for staging when available in the workspace. Use platform addresses and enabled access restrictions for review. Confirm the workspace's actual sandbox limits before uploading data. The standard public launch requires a site plan. Confirm whether a campus agreement covers it before committing to any purchase. [Sandbox and site plans](https://github.com/pantheon-systems/documentation/blob/main/src/source/content/guides/getstarted/07-purchase.md) · [Dev, Test and Live workflow](https://github.com/pantheon-systems/documentation/blob/main/src/source/content/pantheon-workflow.md)
- Use Pantheon's standard WordPress upstream for the simplest match with this prototype, unless Berkeley directs otherwise. Its October 2026 release notes identify PHP 8.3 as the default for new Pantheon WordPress sites. Check the actual WordPress and PHP versions in Dev, confirm the database configuration and test the theme and plugin on that stack before promotion. If campus uses the Composer-managed upstream, follow its web root and dependency conventions. [WordPress upstream](https://github.com/pantheon-systems/WordPress) · [PHP 8.3 release note](https://github.com/pantheon-systems/documentation/blob/main/src/source/releasenotes/2026-10-02-php-83-default-wordpress-upstreams.md)

## Launch gates

| Gate | Required evidence |
| --- | --- |
| Sponsorship, hosting and DNS | Berkeley sponsor, approved ownership of the hosting workspace, confirmed plan, named campus DNS administrator and approved domain change request for `rjhub.berkeley.edu`. |
| Security and incidents | Named response and recovery contacts, review of roles and authentication, tested backup and restore, approved staging access controls, and documented incident path. |
| Privacy and intake | Approved privacy notice and retention policy, verified contact routes and continued demo-only intake. Any future data collection needs separate approval, a security review and an approved form service. |
| Accessibility | Institutional review, keyboard, mobile and screen-reader checks, accessible linked PDFs and a remediation owner. |
| Editorial approval | Authorized source export and reconciliation, bylines and dates verified, duplicate pages resolved, partner and active service claims signed off, map citations reviewed, and current footer notices and contacts supplied. |
| Media and brand | Written clearance of public image and logo assets with correct attribution, alternative text and license records. Remove every preview-only derivative and associated upload from the staging copy. |
| Staff readiness | Editor signoff in staging, handoff and training completed, and named owners able to maintain and recover the site. |

## Rehearse in Dev and Test

1. **Inventory the source.** The [content migration report](CONTENT_MIGRATION_REPORT.md) describes source gaps and the importer. Obtain an authorized export and a corresponding approved uploads inventory. Reconcile counts by type and status and compare titles, full text, bylines, dates and media links for representative entries. Keep unpublished records in protected review and preserve their status. Reconcile [the redirect inventory](../content/REDIRECTS.csv) with the approved production paths.
2. **Prepare a release dataset.** Use a separate local copy. Strip preview accounts and unrelated personal data, replace the provisional logo, remove uncleared photos and attachments, remove private design alternatives from the release, and replace pending notices with approved editorial copy where available. Set up host accounts by approved channels. Exclude local secrets and any private source exports from Git and release artifacts.
3. **Transfer code.** In Pantheon Dev, add the custom RJ Hub theme and content plugin from the package's `wp-content` folders at the equivalent WordPress code location. Use Pantheon's Git workflow to deploy the code. Keep the upstream's WordPress core, host configuration and managed database settings. Keep local Docker configuration, local `.env`, tests and private media source files outside the web root. [Manual migration](https://github.com/pantheon-systems/documentation/blob/main/src/source/content/migrate-manual.md) · [Pantheon WordPress configuration](https://github.com/pantheon-systems/documentation/blob/main/src/source/content/guides/php/04-wp-config-php.md)
4. **Transfer the database.** Back up the destination first. For the local copy, `bash scripts/backup.sh` produces `wordpress.sql` and `uploads.tar.gz` under `backups/`. Use the sanitized SQL export through the environment's database import, confirm the table prefix matches and run the required WordPress database upgrades. The database holds navigation, pages, block settings, authors and imported content. Use WP-CLI's serialization-safe search and replace, with a dry run, for changes from the local base URL to the Dev or Test platform address. Exclude GUIDs from replacement and verify home and site URLs, attachments, menu links and login redirects. Rehearse on Test before using a production hostname. Avoid global SQL text replacement, which can corrupt serialized block and plugin settings. [Manual database import](https://github.com/pantheon-systems/documentation/blob/main/src/source/content/migrate-manual.md)
5. **Transfer uploads separately.** Import the approved upload archive or copy it with authorized SFTP. Repack the contents of `uploads/` if preparing an archive for Pantheon's Dashboard import. Keep the relative year and month directories and avoid creating an extra nested `uploads` folder. On Pantheon's standard WordPress layout, `wp-content/uploads` is backed by the site's persistent files storage. Check sample images, PDF URLs, thumbnails and rights records, then check that an Editor can upload and insert an approved image. [Manual files import](https://github.com/pantheon-systems/documentation/blob/main/src/source/content/migrate-manual.md)
6. **Verify and rehearse recovery.** Deploy code to Test and separately load the intended content and uploads. Keep Dev and Test access-restricted, keep intake disabled, and prohibit search engine indexing of non-production sites. Review desktop and mobile navigation, archives, approved map entries, PDF links, privacy and accessibility routes and editor flows. Confirm scheduled publishing and cache invalidation. Take matched code, database and files backups and test restoring them to a protected environment. [Backups](https://github.com/pantheon-systems/documentation/tree/main/src/source/content/guides/backups) · [WordPress launch checks](https://github.com/pantheon-systems/documentation/blob/main/src/source/content/guides/wordpress-pantheon/04-wordpress-launch-check.md)

Promoting code through the platform does not automatically promote database content and uploads. Treat the initial transfer into a new Live environment as a controlled one-time import. After launch, make routine editorial changes in Live and deploy tested code separately. Overwriting Live content from Test can lose new posts, edits and uploads. [Code and content workflow](https://github.com/pantheon-systems/documentation/blob/main/src/source/content/pantheon-workflow.md)

## Authorized cutover

1. Schedule a change window with the steward, managing editor, owner and campus DNS contact. Record the current DNS answers and affected records, certificate status, release revision and backups. Agree on signoff, monitoring and rollback criteria. If the campus team elects to lower a DNS TTL, do it sufficiently ahead of the window.
2. Freeze changes that would be lost during migration. Capture the final source changes and reconcile the release dataset, then deploy code and import approved database content and uploads to the new Live environment. Validate on the platform address before routing the campus domain.
3. Configure approved one-hop redirects to equivalent new paths, including high-traffic legacy articles and documents. Keep missing content a clear 404 until an agreed destination exists. Test old URLs, canonical URLs, query handling and redirects for loops.
4. In the new Live site's **Domains / HTTPS** screen, have the authorized staff follow the current ownership verification and certificate pre-provisioning instructions. Confirm the certificate and domain with a host override before DNS changes. Coordinate any required TXT or CAA changes with campus DNS. Let campus apply only the production records Pantheon specifies when the cutover is approved. Confirm HTTPS, certificate name and expiration, HTTP redirects, canonical host, cache, sitemap, login and critical pages from independent networks after propagation. [Domain connection and certificate verification](https://github.com/pantheon-systems/documentation/blob/main/src/source/content/guides/launch/04-domains.md) · [Configure DNS and HTTPS](https://github.com/pantheon-systems/documentation/blob/main/src/source/content/guides/launch/06-configure-dns.md)
5. Remove Live indexing restrictions when approved and verify Dev and Test remain protected. Notify stakeholders through the approved release process. Keep the previous hosting available through the agreed rollback and retention periods.

## Rollback and retirement

An invalid certificate, widespread missing content, failed login or unintended data exposure warrants immediate escalation. Pause editorial changes, preserve recent work and record the symptoms. The steward and campus DNS owner can restore the previous DNS records if the new service must be withdrawn. DNS caches may delay recovery, so keep both hosts available. If the problem is limited to a release, restore the matched code, database or uploads only as needed and validate the result before reopening. Reconcile updates made after the backup to avoid silently losing editorial work.

Retire old hosting only when the site owner has accepted the new site, approved redirects work, rollback is no longer required and final archives and retention arrangements are documented. Have the authorized owner coordinate termination and remove obsolete access.
